# Security review — October 28, 2026

Scope: API routes/services/validators, database migrations, vault cryptography, React data flows and storage, MV3 message/autofill boundaries, proxy/containers, operational scripts, dependencies, CI and regression tests. Baseline: clean `main` at `ac79900`. The user first requested an audit and subsequently authorized local fixes. No production account, supplier, private spreadsheet or production database was accessed. No commit, push or deployment was performed.

## Original login report

The reported account was a QA login; the exact request and request/response direction were not supplied. Local reproduction found no Hub password or password hash in successful login or `/api/auth/me` responses: account data is projected through `publicUser`. The request necessarily carries the credentials entered by the user; their visibility in that user's DevTools Payload tab is expected, including with HTTPS. This is distinct from returning stored credentials to a caller. See [Chrome's payload documentation](https://developer.chrome.com/docs/devtools/network/reference/#payload) and [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).

This does not disprove an incident in the deployed installation. The production image, exact route, caller permissions and sanitized field names would need to be correlated before declaring that incident resolved. The source fixes below are local only.

## Access boundaries checked

- Anonymous callers received 401 for catalog, credential metadata, identity, users, audit, preferences and extension-package routes. Configuration was the exception and is now protected too.
- Catalog and vault list responses contained metadata, without usernames/passwords, encrypted credential columns or password hashes.
- Another user and another administrator could not list, reveal, overwrite, ticket or delete an owner's personal service in the exercised cases. Global catalog mutations and shared credential management retain server-side admin checks.
- Shared credentials remain usable by authenticated catalog users through tickets, as specified by the existing pilot. This is not a per-service entitlement system.
- The existing `/reveal` contract permits shared reveal by admins and individual reveal by the owner/admin support for global services. React does not call it. No UI reveal feature was added.
- `Origin: chrome-extension://...` is a browser restriction, not cryptographic attestation. An HTTP client holding a valid ticket can reproduce it. The audit reproduced this using its own synthetic session/ticket. Assisted autofill necessarily exposes supplier credentials to the extension and destination DOM; secrecy from the person controlling that browser requires a different provider-supported architecture. This limitation is documented rather than represented as fixed by payload obfuscation.
- Hub passwords use salted scrypt; sessions and tickets are stored by hash; vault records use authenticated AES-GCM with service/owner/key-version AAD. Existing tamper and owner-isolation regressions remain in place.

## Why the previous green gates were insufficient

`npm run check` passed on the original source against a separate PostgreSQL 16 database while the failures above were reproducible. It checked types, lint, formatting, current tests and builds; it did not include E2E or dependency auditing. Tests covered admin password reset, but not two existing sessions plus a ticket after a self-service password change. The favicon test covered literal private hosts but not DNS answers or redirects. No audit-failure rollback or lock-wait deadline regression existed. UI tests used mocked fetch, so they could not prove server authorization.

The old E2E suite intercepted every `/api` request and replayed it through Playwright. That exercised a real API but bypassed the browser's proxy transport. The new suite uses the actual Vite proxy. It initially failed two card-creation scenarios: the web client did not consume the successful POST response, and Playwright's no-store response-body read remained pending. The client now consumes and validates the returned service before accepting success; the un-intercepted suite then passed all eight scenarios.

An additional browser regression now inspects login and catalog response fields and no-store headers over the real proxy, bringing E2E to nine scenarios. Setup reuses one administrator session while browser sessions stay independent; this avoids exhausting the unchanged 20/minute login limiter with repeated fixture logins. The dedicated limiter regression still tests rejection and expiry.

These are specific coverage and acceptance failures. Their presence supports criticism of the prior quality claims, but does not establish intentional test manipulation. Passing crypto round-trip tests or a large test count was insufficient evidence for broad security assurances.

## Validation and practical limits

Initial reproductions used a temporary, dedicated PostgreSQL 16 container on loopback port 55488, disposable databases, and synthetic users/destinations. SSRF reproduction used actual local HTTPS/fetch with a temporary trusted test certificate and controlled DNS; Google's unrelated fallback was suppressed. The original code contacted loopback, and a private redirect was requested three times before final rejection. No operational target was contacted.

Repository regression sources include actual PostgreSQL authorization/revocation/audit-failure/deadline checks, a real socket test proving denied DNS answers never connect, explicit redirect/stream-boundary unit tests, account-switch frontend tests and destination matcher tests. Mocked transport tests establish response-policy behavior, not production network reachability. The lock-wait regression uses a shortened synthetic expiry while preserving the actual database clock/locking mechanism; production TTL remains 30 seconds.

Final local gates passed: `npm run check` (52 API, 39 extension and 68 Web tests, plus typechecks/lint/format/build), `npm run test:e2e` (nine scenarios), and `npm audit --audit-level=moderate` (zero reported vulnerabilities). The build retains the inherited non-blocking chunk-size warning. Hosted CI has been configured but was not run remotely. Local logs and initial reproduction scripts are temporarily retained under `/tmp/hublink-security-audit-20261028-gxIHHw/`; these are not durable production evidence. Browser E2E still does not cover an installed Chrome extension, real supplier login, host TLS/proxy configuration or production recovery. The reviewed backup/restore scripts were not executed against any installation during this task. This review is not a penetration-test certification or a guarantee that every possible defect has been found.

Production remains on its previously deployed images until a separately authorized release. Existing sessions are not retroactively revoked by editing source. The documented public-pilot 2FA exception, runtime key custody, off-host recovery and provider-specific acceptance remain open operational decisions.

A release must rebuild both API and Web images and refresh the unpacked extension so both destination checks use the new matcher. Preserve the installation's existing vault master key; these fixes do not require a key change or a new schema migration. The temporary database container and test TLS key were removed after local validation.
